# 4장. 데이터 모델링과 E-R 모델

> 이 장에서 배우는 것
> - 현실 세계를 데이터베이스로 옮기는 세 단계(개념적·논리적·물리적 설계)를 이해한다.
> - 개체·속성·관계라는 세 가지 재료로 세상을 모델링하는 방법을 익힌다.
> - 개체-관계(E-R) 다이어그램을 그리고 읽을 수 있다.

> - 위 개념들이 실제 도서관 데이터베이스에서 어떻게 구현되는지 확인한다.

## A. 개념 학습부 — 데이터 모델링의 원리

> 이 절에서는 도서관과 무관하게, **누구에게나 익숙한 온라인 쇼핑몰**을 예로 들어
> 데이터 모델링의 기본 개념을 설명한다. "고객이 상품을 주문한다"는 상황만 알면
> 충분하며, 도서관 지식은 전혀 필요하지 않다.

### 4.1 데이터 모델링이란

**데이터 모델링(data modeling)**이란 현실 세계의 일부를 데이터베이스에 담기 위해
**추상화(abstraction)**하는 과정이다. 현실은 복잡하고 무한한 정보를 담고 있지만,
데이터베이스는 그중 **업무에 필요한 부분만** 골라 단순한 구조로 표현해야 한다.

예를 들어 온라인 쇼핑몰을 만든다고 하자. 현실의 "고객"은 성격, 취향, 건강 상태 등
무수한 정보를 가진 존재이지만, 쇼핑몰 데이터베이스는 그중 **이름·이메일·주소·전화번호**
정도만 관리하면 충분하다. 무엇을 담고 무엇을 버릴지 결정하는 작업이 곧 모델링이다.

데이터 모델링은 보통 세 단계를 거쳐 구체화된다.

| 단계 | 산출물 | 특징 |
|---|---|---|
| **① 개념적 설계** | 개체-관계(E-R) 다이어그램 | 특정 DBMS와 무관, 사람이 이해하기 위한 그림 |
| **② 논리적 설계** | 관계 스키마(테이블·컬럼·키 목록) | 관계형 모델의 규칙을 따르는 표 형태 |
| **③ 물리적 설계** | 실제 DDL(`CREATE TABLE` 등) | 특정 DBMS(MySQL 등)의 문법으로 구현 |

```
현실 세계               ①개념적 설계            ②논리적 설계             ③물리적 설계
(고객이 상품을    →    E-R 다이어그램     →    관계 스키마        →    CREATE TABLE
 주문한다)              (그림으로 표현)          (표로 표현)              (MySQL 코드)
```

*[그림 4-1] 데이터 모델링 3단계 파이프라인*

왜 이런 단계를 거칠까? 처음부터 `CREATE TABLE` 문을 작성하면, 요구사항을 잘못
이해했을 때 코드를 전부 뜯어고쳐야 한다. 반면 그림(ERD)으로 먼저 설계하면 업무
담당자·개발자·학생 모두가 쉽게 검토하고 오류를 일찍 발견할 수 있다. 이 장은
①단계(E-R 모델)를 다루고, ②단계로 변환하는 규칙까지 배운다. ③단계(실제 SQL 구현)는
7장에서 다룬다.

> **9장 예고**: 이 3단계는 사실 "데이터베이스 설계"라는 더 큰 과정의 핵심부다.
> 9장에서는 요구사항 분석부터 이 3단계를 거쳐 구현까지, 전 과정을 도서관을
> 예로 다시 한 번 상세히 다룬다. 이번 장은 그 토대가 되는 **모델링 기법 자체**에
> 집중한다.

### 4.2 개체(Entity)와 속성(Attribute)

#### 개체

**개체(entity)**란 데이터로 관리할 가치가 있는, 독립적으로 존재하며 다른 것과
구별되는 대상이다. 온라인 쇼핑몰이라면 "고객", "상품", "주문" 등이 개체가 된다.

여기서 중요한 구분이 하나 있다. "고객"이라고 할 때 우리는 두 가지를 동시에
가리킬 수 있다.

- **개체 유형(entity type)**: "고객"이라는 **틀(형식)** 그 자체 — 어떤 속성을 갖는지에
  대한 정의. 마치 붕어빵을 찍어내는 **빵틀**과 같다.
- **개체 인스턴스(entity instance)**: 그 틀로 찍어낸 **개별 사례** — "김민준이라는 고객",
  "이서연이라는 고객" 등 실제 데이터 한 건 한 건. 붕어빵 틀로 찍어낸 **붕어빵 하나하나**다.

우리가 ERD에서 그리는 사각형 하나는 개체 **유형**을 나타내고, 실제 테이블에 쌓이는
행(row) 하나하나가 개체 **인스턴스**다. 이 구분은 사소해 보이지만, 4.9절에서 도서관
데이터를 모델링할 때 학생들이 가장 자주 헷갈리는 지점의 열쇠가 된다.

#### 속성

**속성(attribute)**은 개체가 갖는 개별 특성이다. "고객" 개체는 이름·이메일·주소·
전화번호 같은 속성을 가진다. 속성은 성격에 따라 다음과 같이 나뉜다.

| 속성 종류 | 의미 | 예시(고객 개체) |
|---|---|---|
| **단순 속성** | 더 이상 나눌 수 없는 값 | 이메일 |
| **복합 속성** | 여러 요소로 구성된 값 | 주소(시/구/상세주소로 분해 가능) |
| **단일값 속성** | 값을 하나만 가짐 | 고객번호 |
| **다중값 속성** | 값을 여러 개 가질 수 있음 | 전화번호(집전화·휴대전화 등 복수 가능) |
| **저장 속성** | 실제로 저장하는 값 | 생년월일 |
| **유도 속성** | 다른 속성으로부터 계산되는 값 | 나이(생년월일로부터 계산) |

이 가운데 **다중값 속성**과 **유도 속성**은 관계형 데이터베이스의 테이블 하나에
그대로 담을 수 없다. 4.6절에서 이를 어떻게 처리하는지 다룬다.

> **핵심 정리**: 개체 = "무엇을 관리할 것인가", 속성 = "그것의 어떤 정보를 관리할
> 것인가". 개체를 먼저 찾고, 그다음 각 개체의 속성을 나열하는 순서로 모델링한다.

### 4.3 관계(Relationship)와 카디널리티

개체만으로는 세상을 표현할 수 없다. "고객"과 "상품"이 각각 존재해도, 둘 사이의
**"주문한다"**는 연결이 있어야 비로소 쇼핑몰이 된다. 이 연결을 **관계(relationship)**
라고 부른다.

#### 카디널리티(cardinality)

관계에서 가장 중요한 정보는 **몇 대 몇으로 연결되는가**이며, 이를 카디널리티라
한다. 세 가지 기본 유형이 있다.

| 유형 | 표기 | 의미 | 예시 |
|---|---|---|---|
| **1:1** | 일대일 | 한쪽 개체 하나가 다른 쪽 개체 하나와만 대응 | 사람 : 주민등록번호 |
| **1:N** | 일대다 | 한쪽 개체 하나가 다른 쪽 개체 여러 개와 대응 | 고객 : 주문 (고객 한 명이 주문을 여러 번) |
| **N:M** | 다대다 | 양쪽 모두 여러 개씩 대응 | 주문 : 상품 (한 주문에 여러 상품, 한 상품이 여러 주문에 포함) |

#### 참여 제약(participation constraint)

카디널리티가 "몇 개까지 연결되는가"라면, 참여 제약은 **"반드시 연결되어야
하는가"**를 나타낸다.

- **전체 참여(필수)**: 개체의 모든 인스턴스가 그 관계에 반드시 참여. 예) 모든
  "주문"은 반드시 한 명의 "고객"에 속한다(고객 없는 주문은 존재할 수 없음).
- **부분 참여(선택)**: 참여하지 않아도 되는 인스턴스가 있을 수 있음. 예) 모든
  "고객"이 주문을 한 번이라도 한 것은 아니다(가입만 하고 주문은 안 한 고객도 있음).

#### 관계 자체가 갖는 속성

N:M 관계는 흥미로운 특징이 있다. 관계 자체가 속성을 가질 수 있다. "주문"과
"상품"의 N:M 관계를 생각해 보자. "이 주문에 이 상품을 **몇 개** 담았는가", "**개당
가격**은 얼마였는가"는 "주문"의 속성도, "상품"의 속성도 아니다. **두 개체가
만나는 지점에서만 의미를 갖는 값**이다. 이런 속성은 관계 자체에 붙는다.

> 이 관찰은 다음 절(ERD 표기법)과 4.6절(N:M 관계의 변환 규칙)에서 매우 중요하게
> 다시 등장한다.

### 4.4 개체-관계 다이어그램(ERD) 표기법

개체·속성·관계를 그림으로 표현한 것이 **E-R 다이어그램(ERD)**이다. 대표적인
표기법 두 가지를 비교한다.

| 구분 | 피터 첸(Peter Chen) 표기법 | 까마귀발(Crow's Foot) 표기법 |
|---|---|---|
| 개체 | 사각형 | 사각형 |
| 속성 | 타원(개체와 선으로 연결) | 보통 표 안에 컬럼으로 나열(별도 도형 없음) |
| 관계 | 마름모(별도 도형) | 개체를 잇는 **선** 자체가 관계 |
| 카디널리티 표기 | 선 옆에 "1", "N" 숫자 표기 | 선 끝의 **기호 모양**(일자·동그라미·까마귀발)으로 표기 |
| 특징 | 개념을 명확히 구분해 **교육용**으로 좋음 | 표(테이블)에 가까워 **실무 도구**(ERD 툴)에서 널리 사용 |

```
[피터 첸 표기법]                    [까마귀발 표기법]

 고객                                고객                    주문
┌──────┐    1    ◇     N   ┌──────┐  ┌──────┐  1        N  ┌──────┐
│      │─────( 주문한다 )─────│      │  │고객번호│──────○|<─────│주문번호│
└──────┘                    └──────┘  │이름   │              │고객번호│
                                        └──────┘              │주문일자│
   (관계를 마름모로 별도 표현)                                └──────┘
                                       (선 끝 기호로 카디널리티 표현:
                                        │=하나, ○=선택, <까마귀발>=다수)
```

*[그림 4-2] 피터 첸 표기법과 까마귀발 표기법 비교*

이 책은 이후 모든 도서관 ERD를 그릴 때 **까마귀발 표기법**을 기본으로 사용한다.
실무에서 쓰는 ERD 도구(MySQL Workbench, dbdiagram.io 등) 대부분이 이 표기법을
쓰기 때문에, 실습과 바로 연결하기 좋다. 다만 다른 문헌을 읽을 때를 대비해 첸
표기법도 읽을 줄 알아야 한다.

### 4.5 약한 개체(Weak Entity)와 식별 관계

대부분의 개체는 자신만의 고유한 값(예: 고객번호)으로 다른 인스턴스와 구별된다.
그런데 어떤 개체는 **혼자서는 구별될 수 없고, 다른 개체에 종속되어야만** 식별되는
경우가 있다. 이를 **약한 개체(weak entity)**라 한다.

온라인 쇼핑몰의 "주문 상세(주문 안의 각 상품 줄)"를 생각해 보자. 주문 상세
하나는 "몇 번째 줄인가" 하는 자기만의 번호가 없다. 대신 **"어느 주문의"** "몇 번째
상품인가"로만 식별된다 — 즉 소유 개체인 "주문"이 없으면 존재 의미가 없다.

- 약한 개체가 소유 개체에 의존하는 관계를 **식별 관계(identifying relationship)**라
  하며, 보통 이중선 사각형과 이중선 마름모(첸 표기법) 또는 실선(까마귀발)으로 구분해
  표시한다.
- 약한 개체의 기본키는 **소유 개체의 키를 포함**해서 만들어진다(4.6절에서 다시 설명).

> **일반 개체 vs 약한 개체 판별법**: "이 개체가 소유 개체 없이도 혼자 존재하고
> 식별될 수 있는가?"를 자문해 보면 된다. "아니오"라면 약한 개체다.

### 4.6 ERD를 논리적 데이터 모델(관계 스키마)로 변환하는 규칙

개념적 설계(ERD)를 논리적 설계(관계 스키마, 즉 "테이블 목록")로 바꾸는 데는
정해진 규칙이 있다. 다섯 가지 핵심 규칙을 온라인 쇼핑몰 예시로 익혀보자.

| 규칙 | 내용 |
|---|---|
| **① 개체 → 테이블** | 개체 유형 하나는 테이블 하나가 되고, 속성은 컬럼이 된다. |
| **② 1:N 관계 → N쪽에 외래키** | "N" 쪽 테이블에 "1" 쪽 테이블의 기본키를 외래키로 추가한다. |
| **③ N:M 관계 → 교차 테이블 생성** | 새 테이블을 만들어 양쪽의 기본키를 모두 외래키로 담는다. 관계 자체의 속성(4.3절)은 이 교차 테이블의 컬럼이 된다. |
| **④ 다중값 속성 → 별도 테이블** | 하나의 컬럼에 여러 값을 담을 수 없으므로, 별도 테이블로 분리해 1:N 관계로 표현한다. |
| **⑤ 약한 개체 → 복합키** | 약한 개체의 기본키는 소유 개체의 기본키 + 자신의 구분자로 구성한다. |

이 규칙을 적용해 온라인 쇼핑몰 ERD를 관계 스키마로 변환하면 다음과 같다.

```
고객(고객번호 PK, 이름, 이메일)
상품(상품코드 PK, 상품명, 가격)
주문(주문번호 PK, 주문일자, 고객번호 FK)              ← 규칙②: 1:N의 N쪽(주문)에 FK
주문상세(주문번호 FK, 상품코드 FK, 수량, 판매단가,      ← 규칙③: N:M 교차 테이블
        PK=(주문번호, 상품코드))                        ← 규칙⑤: 복합 PK(약한 개체)
```

밑줄 친 것처럼, **N:M 관계(주문:상품)는 교차 테이블(주문상세)로, 1:N 관계
(고객:주문)는 외래키로** 표현된다는 것이 이번 절의 핵심이다. 이 두 규칙은
이후 도서관 스키마 전체를 이해하는 열쇠이므로 반드시 기억해 두자.

## B. 도서관 응용·사례부 — 개념이 도서관에서 이렇게 쓰인다

> 지금부터는 A절에서 배운 개념(개체·속성·관계·카디널리티·ERD·약한 개체·변환 규칙)이
> **실제 도서관 데이터베이스**에서 어떻게 구체적으로 구현되는지 확인한다. 이 절에서
> 완성하는 ERD와 관계 스키마는 이후 7장부터 13장까지 이 책 전체가 사용하는
> **관통 데이터베이스**의 설계도다.

### 4.7 도서관의 개체 찾기 — 실제 서지 표준에서 개체 도출

개체를 찾는 가장 좋은 방법은 "이 시스템이 무엇에 대한 정보를 관리해야 하는가"를
현장 자료에서 직접 확인하는 것이다. 국내 도서관들은 서지 정보를 **KORMARC**
(한국문헌자동화목록법)라는 표준 형식으로 기록한다. KORMARC의 필드 몇 가지만
살펴봐도 도서관이 어떤 개체를 다루는지 자연스럽게 드러난다.

| KORMARC 필드 | 의미 | 도출되는 개체·속성 |
|---|---|---|
| **245** | 표제와 책임표시사항($a 본표제, $d 책임표시) | **book**(자료).title |
| **100 / 700** | 개인명 주표목 / 부출표목(저자·역자 등) | **author**(저자).name |
| **260** | 발행사항($b 발행처) | **publisher**(출판사).name |
| **020** | ISBN | **book**.isbn |
| **056** | 한국십진분류기호(KDC) | **kdc_class**(분류) |

여기서 흥미로운 점 하나. **245 필드(표제)는 "그 책의 제목"이지, "그 책이 몇 권
있는가"에 대한 정보가 아니다.** 몇 권 소장하고 있고 어디에 꽂혀 있는지는 서지
정보(245)가 아니라 **소장 정보(holdings)** — 등록번호·청구기호·소장위치 — 라는
별도 정보에 담긴다. 이 구분이 4.9절의 핵심이다.

이렇게 KORMARC 필드를 훑어보는 것만으로 우리는 이미 세 개의 핵심 개체를
찾아냈다: **자료(book)**, **저자(author)**, **출판사(publisher)**. 여기에 도서관
운영에 필요한 개체를 더하면 다음과 같다.

| 개체 | 의미 |
|---|---|
| **book** | 자료(서지 단위) — "무슨 책인가" |
| **author** | 저자/역자 |
| **publisher** | 출판사 |
| **copy** | 소장본 — "실제로 꽂혀 있는 책 한 권" |
| **branch** | 분관 — 소장본이 있는 도서관 |
| **member** | 회원(이용자) |
| **loan** | 대출(대출·반납 기록) |
| **reservation** | 예약 |
| **fine** | 연체료 |
| **kdc_class** | 분류(KDC 참조) |

### 4.8 도서관의 관계 모델링

개체를 찾았으니, 4.3절의 카디널리티 개념으로 이들의 관계를 하나씩 규정해 보자.

**① book : copy = 1:N (전체참여 : 부분참여)**
자료 하나는 소장본을 여러 권 가질 수 있다(같은 책을 3권 산 경우). 모든 소장본은
반드시 어떤 자료에 속해야 하지만(전체참여), 아직 한 권도 사지 않은 자료 서지도
있을 수 있다(부분참여) — 예를 들어 구입 예정 도서를 서지만 먼저 등록해 둔 경우.

**② book : author = N:M**
책 한 권에 저자가 여럿(공저), 저자 한 명이 책을 여럿 쓸 수 있다. 4.6절 규칙③에
따라 교차 테이블 **book_author**로 해소하며, "역할(저자/역자/편저)"이라는 **관계
자체의 속성**을 이 교차 테이블에 담는다 — 정확히 4.3절 마지막에서 예고한 그 경우다.

**③ member : loan = 1:N, copy : loan = 1:N**
회원 한 명은 대출을 여러 번 하고, 소장본 한 권도 시간이 지나며 여러 번 대출된다.
따라서 **loan** 테이블에는 규칙②에 따라 `member_id`와 `copy_id` 두 개의 외래키가
들어간다.

**④ book : reservation = 1:N, member : reservation = 1:N**
예약은 **소장본(copy)이 아니라 자료(book) 단위**로 건다는 점에 주의하자. "3번째
칸에 있는 그 책"을 예약하는 게 아니라 "이 책의 아무 소장본이나 반납되면"
예약하는 것이기 때문이다.

**⑤ loan : fine = 1:N**
대출 한 건에 대해 연체료가 발생할 수 있고(늦게 반납), 상황에 따라 추가 부과가
생길 수도 있으므로 1:N으로 둔다.

### 4.9 헷갈리기 쉬운 지점 — "자료"와 "소장본"을 왜 다른 개체로 나누는가

이 장에서 학생들이 가장 자주 걸려 넘어지는 지점이 바로 여기다. 4.2절에서 배운
**개체 유형과 개체 인스턴스의 구분**을 다시 떠올려 보자.

> "『MySQL로 배우는 데이터베이스 개론』이라는 책이 도서관에 있다"고 할 때,
> 이 문장은 사실 두 가지를 동시에 말하고 있다.

1. **"그런 제목의 책이 세상에 존재한다"** — 이것은 **서지 정보**, 즉 `book` 한 행이다.
2. **"우리 도서관이 그 책을 3권 가지고 있다"** — 이것은 **소장 정보**, 즉 `copy`
   세 행이다.

실제 `sql/seed.sql`의 데이터로 확인해 보자.

```sql
-- book 테이블: "MySQL로 배우는 데이터베이스 개론"이라는 서지는 딱 1건
SELECT book_id, title FROM book WHERE book_id = 1;
-- book_id=1, title='MySQL로 배우는 데이터베이스 개론'

-- copy 테이블: 그런데 실제로 소장한 책은 3권
SELECT copy_id, reg_no, branch_id, status FROM copy WHERE book_id = 1;
-- copy_id=1,  reg_no='EM000001', branch_id=1(중앙도서관), status='대출중'
-- copy_id=2,  reg_no='EM000002', branch_id=1(중앙도서관), status='대출가능'
-- copy_id=21, reg_no='EM000021', branch_id=3(대학도서관), status='대출가능'
```

`book`은 "**개체 유형에 대한 서술**"에 더 가깝고(제목이 무엇인가), `copy`는
"**셀 수 있는 실제 인스턴스**"다(등록번호로 구별되는 물리적 사물 하나하나).
`book` 하나에 `copy`가 0개, 1개, 또는 여러 개 딸려 있을 수 있다는 사실 자체가
바로 4.8절 ①의 **1:N 관계**다.

이 구분이 왜 실무적으로 중요한지 확인해 보자. "이 책을 지금 빌릴 수 있나요?"라는
질문에 답하려면, `book`이 아니라 **`copy`의 `status`를 확인**해야 한다. `book_id=1`은
"대출 가능"이라는 상태를 가질 수 없다 — 그것은 각 소장본의 상태이기 때문이다.
서지 단위와 소장 단위를 하나의 테이블로 뭉쳐 버리면, 같은 책을 3권 가진 경우
제목·저자·출판사 정보가 3번 중복 저장되는 문제가 생긴다. 이 문제는 10장
정규화에서 정면으로 다룬다.

> **핵심 정리**: `book` = 개체 유형에 대응하는 "저작 차원", `copy` = 개체 인스턴스에
> 대응하는 "물리적 차원". 도서관 시스템을 설계할 때 이 둘을 분리하는 것은
> 선택이 아니라 필수다.

### 4.10 도서관 개념 ERD 완성

지금까지 도출한 개체·관계를 종합하면 이 책 전체가 사용할 도서관 개념 ERD가
완성된다.

```
publisher ──1───N── book ──N───M── author
 (출판사)          (자료)  (book_author)  (저자)
                     │1
                     │
                     N
                   copy ───N────1─── branch
                  (소장본)          (분관)
                     │1
                     │
                     N
                   loan ───N────1─── member
                  (대출)            (회원)
                                      │1
                     ┌────────────────┤
                     │1               │N
                     N          reservation
                   fine          (예약, book·member와 연결)
                  (연체료)
```

*[그림 4-3] 도서관 개념 ERD (까마귀발 표기법, 전체)*

| 관계 | 카디널리티 | 비고 |
|---|---|---|
| publisher : book | 1:N | 부분참여(출판사 미상 자료 가능) |
| book : author | N:M | 교차 테이블 book_author, 속성 `role` 보유 |
| book : copy | 1:N | 4.9절 참고 |
| branch : copy | 1:N | 소장본은 반드시 한 분관에 소속(전체참여) |
| copy : loan | 1:N | |
| member : loan | 1:N | |
| book : reservation | 1:N | copy가 아닌 book 단위(4.8절 ④) |
| member : reservation | 1:N | |
| loan : fine | 1:N | |

이 ERD는 부록 A `sql/schema.sql`에서 실제 `CREATE TABLE`로 이미 구현되어 있다.
어떻게 구현했는지는 4.12절 실습에서 직접 확인한다.

### 4.11 실제 사례 엿보기 — 국립중앙도서관의 링크드 데이터(LOD)

지금까지 살펴본 ERD는 **관계형 모델**로 향하는 설계도다. 그런데 국립중앙도서관은
소장 서지 데이터를 관계형 테이블뿐 아니라 **국가서지 링크드 오픈 데이터(LOD)**
라는 또 다른 방식으로도 발행한다. 개념을 확장해서 비교해 보면 관계형 모델의
특징이 더 선명해진다.

- **관계형 모델(이 책의 방식)**: "book"이라는 **표(테이블)**에 title·isbn 같은
  **고정된 컬럼**을 두고, 행 하나가 책 한 종을 나타낸다.
- **LOD(국립중앙도서관 방식)**: 모든 정보를 "**주어-서술어-목적어**"로 이루어진
  트리플(triple) 형태로 표현한다. 예를 들어 "이 책의 표제는 ○○이다"는
  `<이책> — dc:title — "○○"` 처럼 표현되고, `Dublin Core`·`BIBO`(Bibliographic
  Ontology) 같은 **공통 어휘(온톨로지)**를 사용해 다른 기관의 데이터와도 연결
  (link)될 수 있다.

관계형 모델은 "표"라는 고정된 틀에 데이터를 담는 반면, LOD는 데이터를
**그래프(그물망)**처럼 자유롭게 연결한다는 점이 가장 큰 차이다. 이 책은 처음부터
끝까지 관계형 모델을 다루지만, 이렇게 다른 모델링 방식이 실제로 존재하고 국내
도서관계가 이미 활용하고 있다는 사실은 기억해 두자. 이 이야기는 13장(데이터베이스
확장과 최신 기술)에서 NoSQL·그래프 데이터베이스와 함께 다시 다룬다.

## C. 실습부

### 4.12 실습 — ERD를 관계 스키마로 직접 설계해 보기

4.6절의 변환 규칙을 이용해, 4.10절의 도서관 ERD를 관계 스키마(테이블 목록)로
직접 종이 위에 옮겨 보자. 아래는 순서대로 따라 할 수 있는 절차다.

**Step 1. 개체마다 표를 하나씩 그린다(규칙①).**
`book`, `author`, `publisher`, `copy`, `branch`, `member`, `loan`, `reservation`,
`fine`, `kdc_class` — 총 10개 표가 나와야 한다.

**Step 2. 각 표에 기본키(PK)를 정한다.**
대부분 "OO_id" 형태의 자동 증가 번호를 쓴다. 단, `book`은 `isbn`이라는 **자연키
후보**도 있다는 점을 5장(관계 데이터 모델과 키)에서 더 깊이 다룬다.

**Step 3. 1:N 관계마다 "N쪽" 표에 외래키를 추가한다(규칙②).**
예) `book : copy = 1:N` → `copy` 표에 `book_id` 컬럼 추가.
아래 표를 완성해 보자.

| 1:N 관계 | 외래키가 추가되는 표 | 추가되는 컬럼 |
|---|---|---|
| publisher : book | book | publisher_id |
| branch : copy | copy | branch_id |
| book : copy | copy | book_id |
| copy : loan | loan | ( ? ) |
| member : loan | loan | ( ? ) |
| book : reservation | reservation | ( ? ) |
| member : reservation | reservation | ( ? ) |
| loan : fine | fine | ( ? ) |

> ( ? )를 직접 채워 보자. 정답은 `sql/schema.sql`에서 바로 확인할 수 있다.

**Step 4. N:M 관계는 교차 테이블을 새로 만든다(규칙③).**
`book : author = N:M` → 새 표 `book_author(book_id, author_id, role)`를 만든다.
기본키는 `(book_id, author_id, role)`처럼 관련된 컬럼들의 조합으로 정한다.

**Step 5. 완성한 설계를 `sql/schema.sql`과 비교한다.**
아래는 실제 파일의 일부다. 여러분이 종이에 그린 설계와 일치하는지 확인해 보자.

```sql
CREATE TABLE copy (
  copy_id    INT          NOT NULL AUTO_INCREMENT,
  book_id    INT          NOT NULL COMMENT 'FK → book',
  branch_id  INT          NOT NULL COMMENT 'FK → branch(소장 분관)',
  reg_no     VARCHAR(20)  NOT NULL COMMENT '등록번호(도서관 내 유일)',
  call_no    VARCHAR(50)      NULL COMMENT '청구기호',
  status     ENUM('대출가능','대출중','분실','폐기') NOT NULL DEFAULT '대출가능',
  PRIMARY KEY (copy_id),
  ...
  CONSTRAINT fk_copy_book   FOREIGN KEY (book_id)   REFERENCES book (book_id),
  CONSTRAINT fk_copy_branch FOREIGN KEY (branch_id) REFERENCES branch (branch_id)
) ENGINE=InnoDB;
```

**생각해 보기**: `reservation` 표에는 `copy_id`가 없고 `book_id`만 있다. 왜 그런지
4.8절 ④를 다시 읽고 자신의 말로 설명해 보자.

> **7장 예고**: 지금은 "종이 위에서" 스키마를 설계했다. 7장에서는 이 설계를
> 실제 `CREATE TABLE`·`INSERT` 문으로 구현해 MySQL 위에 직접 데이터베이스를
> 만든다.

## D. 마무리

### 4.13 요약

- 데이터 모델링은 현실을 개념적(ERD) → 논리적(관계 스키마) → 물리적(DDL) 순으로
  단계적으로 구체화하는 과정이다.
- **개체**는 관리 대상, **속성**은 개체의 특성이며, 개체는 **유형**과 **인스턴스**로
  구분된다.
- **관계**는 개체 간의 연결이며, **카디널리티**(1:1/1:N/N:M)와 **참여 제약**
  (전체/부분)으로 규정된다. N:M 관계는 **관계 자체가 속성**을 가질 수 있다.
- ERD 표기법은 **피터 첸**(교육용, 마름모로 관계 표현)과 **까마귀발**(실무용, 선
  끝 기호로 표현)이 있다. 이 책은 까마귀발 표기법을 기본으로 쓴다.
- 스스로 식별될 수 없어 다른 개체에 종속되는 개체를 **약한 개체**라 하며,
  그 관계를 **식별 관계**라 한다.
- ERD → 관계 스키마 변환은 다섯 가지 규칙(개체→테이블, 1:N→외래키, N:M→교차
  테이블, 다중값 속성→별도 테이블, 약한 개체→복합키)을 따른다.
- 실제 도서관 서지 표준(KORMARC)에서 book·author·publisher 등의 개체를 도출할
  수 있으며, 특히 **자료(book, 서지)와 소장본(copy, 물리적 인스턴스)을 분리**하는
  것이 개체 유형/인스턴스 구분의 핵심 사례다.
- 국립중앙도서관의 **LOD**는 관계형 모델과 다른 그래프 기반 모델링 방식으로,
  13장에서 더 다룬다.

### 핵심 용어 정리

| 용어 | 정의 |
|---|---|
| 데이터 모델링 | 현실 세계를 데이터베이스로 표현하기 위해 추상화하는 과정 |
| 개체(Entity) | 데이터로 관리할 가치가 있는, 구별 가능한 대상 |
| 개체 유형 / 개체 인스턴스 | 개체를 정의하는 틀 / 그 틀에 따른 개별 데이터 한 건 |
| 속성(Attribute) | 개체가 갖는 개별 특성. 단순/복합, 단일값/다중값, 저장/유도로 구분 |
| 관계(Relationship) | 개체와 개체 사이의 의미 있는 연결 |
| 카디널리티 | 관계에 참여하는 개체 수의 대응 비율(1:1, 1:N, N:M) |
| 참여 제약 | 개체의 모든 인스턴스가 관계에 반드시 참여해야 하는지(전체) 아닌지(부분) |
| E-R 다이어그램(ERD) | 개체·속성·관계를 그림으로 표현한 것 |
| 약한 개체 | 자신만의 키로 식별될 수 없어 다른 개체에 의존하는 개체 |
| 식별 관계 | 약한 개체가 소유 개체에 의존하는 관계 |
| 관계 스키마 | ERD를 논리적으로 변환한, 테이블·컬럼·키의 집합 |
